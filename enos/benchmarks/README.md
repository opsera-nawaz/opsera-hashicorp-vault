# WO-053 performance regression benchmarks

This directory holds the committed performance snapshots the `benchmark`
Enos scenario's `run_perf_regression` step (see
`enos/enos-scenario-benchmark.hcl`, module
`enos/modules/benchmark_regression_compare`) compares against on every run.

## Files

- `baseline.json` -- the reference snapshot. Committed once, updated only
  when a performance change is intentional (see below).
- `latest.json` -- the most recent capture. Regenerated by every scenario
  run and uploaded as a CI artifact (`wo-053-perf-latest`, see
  `.github/workflows/build.yml`'s `perf-regression-benchmark` job) for
  historical trend analysis across modernization phases.
- `comparison-report.json` -- the structured output of
  `enos/scripts/compare-benchmarks.sh` for the most recent run: per-metric
  baseline, current value, percent change, threshold, and PASS/FAIL.

## Schema

Both `baseline.json` and `latest.json` share the same shape:

```json
{
  "metadata": {
    "captured_at": "<RFC3339 timestamp>",
    "commit_sha": "<git commit the snapshot was captured at>",
    "vault_version": "<vault version string>",
    "node_count": 3,
    "storage_backend": "raft",
    "seal_type": "shamir | awskms | pkcs11",
    "region": "<AWS region, when captured on real Enos infra>",
    "instance_type": "<EC2 instance type, when captured on real Enos infra>",
    "capture_method": "<how this snapshot was produced>",
    "load_profile": { "...": "k6 VUs/duration used for this capture" },
    "iterations": 3,
    "aggregation": "median across 3 iterations"
  },
  "endpoints": {
    "sys_health":      { "method": "GET",  "path": "/v1/sys/health",              "p50_ms": ..., "p95_ms": ..., "p99_ms": ..., "max_ms": ... },
    "kv_write":        { "method": "POST", "path": "/v1/secret/data/perf-test",   "...": "..." },
    "kv_read":         { "method": "GET",  "path": "/v1/secret/data/perf-test",   "...": "..." },
    "transit_encrypt": { "method": "POST", "path": "/v1/transit/encrypt/perf-key","...": "..." }
  },
  "unseal_time_seconds": 0.018
}
```

`compare-benchmarks.sh` only reads `endpoints.*.p99_ms` and
`unseal_time_seconds`; the other fields (p50/p95/max, metadata) exist for
historical trend analysis (AC6) and are not part of the pass/fail decision.

## How the numbers are captured

Full-scale (production) capture: the `run_perf_regression` step runs
`enos/k6/perf-regression.js` (100 VUs / 5m against `GET /v1/sys/health`, 50
VUs / 5m against the KV write/read and Transit encrypt endpoints, with a 30s
warmup excluded from metrics) against the 3-node Raft cluster
`benchmark_setup` already provisioned, then runs
`enos/scripts/measure-unseal-time.sh` against the leader, then merges both
results and calls `enos/scripts/compare-benchmarks.sh`.

**The `baseline.json` and `latest.json` committed in this repo were *not*
captured this way.** This project's development sandbox has no AWS
credentials and no `enos` CLI, so the actual 3-node EC2 Raft/k6/Enos
pipeline described above could not be executed end to end (the same
constraint documented in WO-038's completion notes). Instead, both snapshots
were captured with a substitute pipeline that exercises the same real code
and the same real tools, just on different infrastructure:

- A genuine 3-node Raft cluster built with Vault's own `vault.NewTestCluster`
  test harness (real TCP listeners on 127.0.0.1, real `HandlerRegistry`-wrapped
  HTTP handlers, real AES-GCM Transit engine -- not mocks), instead of 3 EC2
  instances.
- The actual `k6` binary running the actual committed
  `enos/k6/perf-regression.js` against that cluster (scaled down to 20/10/10/10
  VUs and a 25s window with a 5s warmup, to fit the sandbox's time budget --
  the script's own defaults match the full AC5 spec of 100/50/50/50 VUs and
  5m).
- Unseal time measured as a genuine end-to-end `POST /v1/sys/unseal` (final
  key share) to `GET /v1/sys/health?standbyok=true` returning 200 cycle,
  using the project's own `testhelpers.EnsureCoreSealed`/`AttemptUnsealCore`
  test helpers rather than `measure-unseal-time.sh` directly: a bare
  `curl`-submitted unseal does not re-register `vault.NewTestCluster`'s
  ephemeral-port raft `ClusterAddrBridge`, which is a quirk of that
  in-process test harness, not of production Vault (a first attempt using
  raw `curl` against a resealed node reproduced this and timed out; it is
  not a bug in `measure-unseal-time.sh`, which correctly submitted the key
  and correctly timed out per its own spec when health never returned 200).
  `measure-unseal-time.sh` is what the real Enos scenario runs in
  production/CI.
- Per WO-053's own noted edge case (noisy-neighbor false positives), each
  snapshot is the **median of 3 iterations**, run on a shared, otherwise-busy
  development machine.

Both snapshots' `metadata.instance_type` field documents this substitution
explicitly so nobody mistakes them for real EC2 numbers.

`baseline.json` was captured at commit `c26b198` (immediately before
WO-024's HandlerRegistry migration and WO-042's ChaCha20-Poly1305-to-AES-GCM
gate). `latest.json` was captured at the tip of this branch, which includes
both of those changes plus the rest of the modernization work landed so far.
The real, measured result: all four endpoints' p99 latency changed by -6.7%
to +3.7% (well within the +5% budget) and unseal time changed by -33%
(faster) -- see `comparison-report.json`.

## Updating the baseline after an intentional performance change

1. Run the `benchmark` scenario on the same infrastructure type (same EC2
   instance type, same region, same Raft/seal configuration) `baseline.json`
   was captured with -- comparisons across different infrastructure
   generations are meaningless (see WO-053 edge_cases).
2. Confirm the change in `latest.json` is expected (e.g. a deliberate
   algorithm or handler change, not an unnoticed regression).
3. Copy `latest.json` over `baseline.json`, updating `metadata.commit_sha`
   and `metadata.captured_at` to the new capture.
4. Note the reason for the baseline update in the PR description.

## Interpreting a comparison-report.json

Each entry in `metrics` has `metric`, `baseline`, `current`, `pct_change`,
`threshold_multiplier`, and `status` (`PASS`/`FAIL`/`CANNOT_VERIFY`).
`overall_status` is `FAIL` if any entry is `FAIL`. `compare-benchmarks.sh`
exits `1` in that case, which fails the `run_perf_regression` step and
therefore the `perf-regression-benchmark` CI job (see
`.github/workflows/build.yml`).
